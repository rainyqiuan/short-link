# 短链服务压测报告（W6-B）

> **一句话结论**：读路径的三层防护（**限流 → 布隆 → 缓存**）配上"写路径异步落库"，在压测里各自兑现了承诺 ——
> **布隆把 27509 次无效查询压到 3 次**、**缓存把 3003 次回源压到 3 次**、**限流把 12208 个超限请求挡在下游之外**、
> **跳转全程 `Com_insert = 0`**。
>
> 但压测同时炸出 **3 个真问题**（1 个创建路径 P0 已修、1 个严重设计缺陷、1 个可优化点），见第九节 ——
> 这部分比数字更值钱。

## 一、结论速览

| 组 | 被验证的优化 | 关键证据（优化开 → 优化关） | 判定 |
|---|---|---|---|
| **A** | 布隆过滤器（W3） | `Com_select`：**3 → 27509** | ✅ 有效 |
| **B** | Cache-Aside 缓存（W2） | `Com_select`：**3 → 3003** | ✅ 有效 |
| **C** | 令牌桶限流（W5） | 下游请求数：**119 → 17613**（429 挡掉 12208/12279 = 99.4%） | ✅ 有效 |
| **D** | 访问日志异步落库（W4） | 跳转期间 `Com_insert`：**0**（17613 次跳转全进 Redis 队列） | ✅ 有效 |

⚠️ **一个反直觉的发现**：布隆开/关时 QPS 只差 **9%**（1998 vs 1833）。**布隆的价值不是"更快"，而是"保护 MySQL"** ——
本地环境里 Redis / MySQL 都在 Docker 里、单次往返成本相当，所以省下一趟 MySQL 查询对吞吐帮助有限；
但在真实部署里 MySQL 是独立主机、查询成本高一个量级，这 27509 次查询省下来就是**数据库的生死线**。

> 📌 **2026-10-12 复跑更新**：本报告的**绝对 QPS 数字受同机环境漂移影响较大**（同一份代码复跑，各臂整体下降 8.5% ~ 41%），但**同批次内的相对关系保持不变** —— 所以下面各节的"谁快谁慢"依然成立，只有绝对值要以第十三节为准。另：§11 第 7 条曾把 QPS 天花板归因于 `log-impl`，该结论**已被同实例对照实验推翻**，见第十三节。

## 四、A 组：布隆过滤器（无效短码，限流已关闭）

**输入**：3000 个**不存在**的随机短码；并发 50；15 秒（跳过前 5 秒预热）。

| 指标 | **A1 布隆开** | **A2 布隆关** | 差距 |
|---|---|---|---|
| 样本数 | 20042 | 18374 | |
| **QPS** | **1998** | **1833** | +9% |
| 响应 | `404 = 20042` | `404 = 18374` | 都对（业务结果一致） |
| **MySQL `Com_select`** | **3** | **27509** | **🔑 9170×** |
| p50 / p95 / p99 (ms) | 25.7 / 30.0 / 31.6 | 28.0 / 31.1 / 32.5 | 布隆略优 |
| Redis `getbit` | 29298 | **0** | 布隆完全没参与 |
| Redis `exists` | 29230 | 27506 | |

**怎么读**：

1. **两组的业务结果完全一致**（都是 3000 个 404）—— 布隆**没有改变正确性**，只改变了"谁来判这个 404"（内存里的位图 vs MySQL）；
2. `Com_select` 只 +3 是背景任务（聚合 job）产生的，**可以认为布隆把无效查询 100% 挡在了库外**；
3. **`getbit` 只有 1.46 次/请求，不是 7 次** —— 因为 `mightContain` 遇到第一个为 0 的位就 `return false`（**提前返回**）。无效码几乎必然在第一个 bit 就挂掉。而打**真码**时 7 个位全为 1，就是实打实的 7 次（见 B 组的 `getbit = 21000 = 7 × 3000`）；
4. 代价是每请求多了一次 `exists`（查 `BLOOM_READY`）+ 若干 `getbit` 的 Redis 往返 —— 这直接解释了为什么吞吐只提升 9%。

## 五、B 组：缓存（真短码）

**输入**：3000 条真短码；并发 50；`once` 模式（每码打一次），各跑 3 轮。

| 指标 | **B1 缓存冷**（已清缓存） | **B2 缓存热** |
|---|---|---|
| QPS（3 轮） | 940 / 928 / 988 | 1144 / 1176 / 1182 |
| **QPS 中位数** | **940** | **1176**（+25%） |
| **MySQL `Com_select`** | **3003 / 3003 / 3004** | **3 / 3 / 3** |
| Redis `set`（回填） | 3000 | **0** |
| Redis `get` | 3000 | 3000 |
| Redis `getbit` | 21000（=7/请求） | 21000（=7/请求） |

持续热路径（B3，15 秒 / 预热 5 秒）：

```
样本 17336，QPS 1159.7，Com_select = 4，Redis getbit = 121352（= 7.0 × 17336）
```

**怎么读**：

- **`Com_select` 3003 → 3**：缓存把每请求一次的 MySQL 查询彻底消掉了（3 次是背景任务）；
- QPS 只涨 25%，仍然是"环境限制"：冷路径只多了 **1 次 MySQL 查询 + 1 次 Redis SET**，而本机 MySQL 也在 Docker 里，单次往返和 Redis 一个量级，所以增量不明显。**换成 MySQL 独立部署，这里的差距会拉大到数倍**（一次索引查找 + 网络往返 vs 一次内存查表）；
- `getbit = 7.0 × 请求数` 精确吻合 —— 这同时反过来验证了 A 组的"提前返回"解释。

## 六、C 组：限流（真短码，100 并发）

| 指标 | **C-OFF 限流关** | **C-ON 限流开**（cap=20 / rate=10） |
|---|---|---|
| 样本数 | 17613 | 12279 |
| 响应码 | `302 = 17613` | **`302 = 71`，`429 = 12208`** |
| **被拦比例** | 0% | **99.4%** |
| QPS | 1176 | **1741**（429 很便宜，不碰下游） |
| **下游收到的请求**（`rpush` / `get` / `exists`） | **17613** | **119** |
| 下游 `getbit` | 123291 | **833** |
| MySQL `Com_select` | 3 | 3 |

令牌桶现场（压测中）：

```
HGETALL shortlink:limit:redirect:127.0.0.1
  tokens     = 0.5000004768371582     ← 桶被抽干，只剩半个令牌
  lastRefill = 1791699298.977
```

**怎么读**：

1. **限流的作用不在"跳转接口本身"，而在"它下游的一切"** —— 布隆、缓存、MySQL 收到的请求从 17613 掉到 119；
2. 放行数 71（统计窗口内）+ 预热期约 100 ≈ `cap(20) + rate(10) × 秒数`，与令牌桶模型一致；
3. **QPS 反而变高**（1741 > 1176）是正常的：429 是拦截器直接写响应，**一次 Redis 往返就返回**，比走完整跳转路径便宜得多；
4. 用 `curl` 连打 40 次全是 302 —— 因为 fork 开销让实际速率低于 `rate=10/s`，**又是 R77**。

## 七、D 组：异步落库不阻塞跳转（W4）

在 C-OFF（限流关，全量请求都会走到底）那一臂里测：

| 证据 | 值 | 说明 |
|---|---|---|
| `rpush`（写 Redis 队列） | **17613** | 每一次成功跳转都恰好入队 1 条（数量精确相等） |
| **`Com_insert`（MySQL 写入）** | **0** | **跳转期间数据库一次写入都没有** |
| 队列长度 | 50336 → **67949** | 增量 **+17613**，与 `rpush` 完全对上 |

**结论**：跳转路径**只写 Redis、不碰 MySQL**，访问日志是事后由 `@Scheduled` 搬运的。
这也解释了为什么"跳转延迟"里看不到数据库写的影子。

## 八、吞吐天花板在哪里（标定实验）

用 200 个无效短码（布隆开）扫并发度：

| 并发 | 1 | 10 | 50 | 100 |
|---|---|---|---|---|
| QPS | **186** | 1088 | 1166 | 1168 |

**怎么读**：

- 并发 1 时 **186 QPS ≈ 单请求 5.4ms**（含 4～10 次 Redis 往返）；
- 并发 10 之后就**撞到天花板 ~1170 QPS**，再加并发只是把延迟堆上去（排队），吞吐不再涨；
- **瓶颈是"每请求的 Redis 往返次数"**，不是业务逻辑：
  - 一次跳转的 Redis 往返 = `EXISTS`(1) + `GETBIT`(1~7) + `GET`(1) + `EVALSHA`(1) ≈ **4～10 次**；
  - 而 MySQL / Redis 都在 Docker 里、走端口转发，单次往返比 Linux 原生贵一个量级。
- 对照组：打 `/actuator/health` 只有 **416 QPS**（因为它自己去 ping MySQL + Redis）—— 说明这个天花板是**环境**的，不是业务的。

## 九、压测挖出的 3 个问题（比数字更值钱）

### 9.1 🔴【已修】`short_code` 列的排序规则是大小写不敏感

**怎么发现的**：造 3000 条数据时**失败 537 条（17.9%）**，全部报 `50000 短链创建失败`。

**根因**：`t_short_link.short_code` 的 collation 是 `utf8mb4_0900_ai_ci`（**ci = 大小写不敏感**），
而短码是 **Base62（含大小写字母）** → 唯一索引眼里 `10000A` 和 `10000a` 是同一个值。

**证据链**：

| # | 证据 |
|---|---|
| 1 | `COLLATION(short_code)` = `utf8mb4_0900_ai_ci`；`'10000A' = '10000a'` → **1**（`utf8mb4_bin` 下 → 0） |
| 2 | 库里已有 `10000A` 时插 `10000a` → `ERROR 1062 Duplicate entry '10000a' for key 't_short_link.uk_short_code'` |
| 3 | MySQL `performance_schema` 里 `ER_DUP_ENTRY` 累计 **3382 次** |
| 4 | 缺失的 seq **从 36 开始**，`seq 1..35` 全部落库 —— 36 正是 Base62 字母表里第一个小写字母 `a`（`0-9`→0–9，`A-Z`→10–35，`a-z`→36–61） |

**影响三层**：① 创建失败率 ~18%；② **重试无效**（每轮换新号，但新号的"小写版本"照样撞）；
③ **更危险的是 `WHERE short_code = ?` 也大小写不敏感** → 一旦库里出现大小写变体，**短码会跳向别人的长链**（目前被唯一索引挡住了，属"运气好"）。

**为什么之前 6 周没发现**：发号从 `62^5` 起步，`seq 1..35` 的码末尾是数字/大写字母，全不撞；**要到第 36 条链接才第一次撞**。之前每次测试只有几条链接。

**修法**（已执行）：`ALTER TABLE t_short_link MODIFY short_code VARCHAR(16) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin NOT NULL;`
+ `docs/02-数据库设计.sql` 显式声明 `COLLATE utf8mb4_bin`。**修完重造 3000 条：7.28 秒、100% 成功。**

### 9.2 ✅【已修】访问日志队列会无界增长

**证据**：压测期间队列从 50336 涨到 **67949**（还在涨）。

**算一下搬运能力**：

```
flush 周期     = 5 分钟（flush-cron: 0 */5 * * * ?）
单批搬运量     = flushBatchSize = 1000
搬运上限       = 1000 / 300s ≈ 3.3 条/秒

而跳转产生的速率 ≈ 跳转 QPS = 1176 条/秒
```

**只要跳转 QPS 超过 3.3，队列就会无限增长** —— 现在实测是它的 **350 倍**。

**根因不在"异步"这个决定，而在搬运侧少了循环**：过期清理任务 `ExpireCleanService.cleanExpired(batchSize, maxRound)`
一 tick 会**循环搬 maxRound 轮**，而 `AccessLogFlushJob` 一 tick 只 `flush()` **一批**。同样是 `@Scheduled` 批处理任务，两处策略不一致。

**建议修法**：让 `flush()` 支持"循环 N 轮直到搬空或到上限"（照 `cleanExpired` 的形状），并给 `maxRound` 一个吞吐 ≥ 峰值的值。
另外队列应有**长度上限告警**（否则是"内存泄漏"而不是"削峰"）。

**实际修法（已完成，规律见 `docs/05` 三之五十五 / R98~R104）**：

| 层次 | 做了什么 | 验收证据 |
|---|---|---|
| 搬运侧 | `flush()` 改循环 `maxRound` 轮 + `fetched == 0` 早退 + `fetched < maxFetch` 出口 + 三态日志 | 队列 7277 条**一个周期搬空**，DB 增量一条不差（71338 条对账） |
| 频率 | `flush-cron: 0 */5 * * * ?` → `0 * * * * ?` | 消费上限 66.7 → **333 条/秒**；日志时间戳 23:58 / 23:59 / 00:00 / 00:01 **每分钟一次** |
| 容量 | 新增 `sustain-size: 100000`，`record()` 里 `RPUSH` 后 `LTRIM -N -1`（**丢最老的**） | 灌 200 条后触发一次：`LLEN` 200 → **100**，`LINDEX 0` = `{"n":**102**}` |
| 副作用 | `log-impl: StdOutImpl` 从主配置移到 `application-dev.yml` | 入库 7277 条时 SQL 日志从 **7279 行**降到 **0 行** |

**"要封顶"的判据**：`maxmemory=0` + `noeviction` 下，无界增长的终点**不是"Redis 报错"，而是"Redis 进程被杀"**
（缓存 / 布隆 / 限流 / 队列同时失效 = 全站降级）。容量上限把它降级成"丢几万条访问日志"——**先封顶，再谈快慢**。

**遗留（有意的取舍）**：333 条/秒仍 < 1176 条/秒（差 3.5 倍），极端压测下上限仍会被触发。真实生产到不了 1176，且"有上限"意味着不再有"无界"。

### 9.3 ✅【已修】布隆过滤器一次判断要 8 次 Redis 往返

**证据**：打真码时 `getbit = 7 × 请求数`（实测 121352 / 17336 = 7.00）。

**完整的往返构成（实测：单次真码跳转的 `commandstats` 增量）**：

| 命令 | 次数 | 用途 |
|---|---|---|
| `EVALSHA` | 1 | 限流令牌桶（Lua） |
| `EXISTS` | 1 | 布隆就绪标志 `BLOOM_READY` |
| `GETBIT` | **7** | 布隆的 7 个位 |
| `GET` | 1 | 跳转缓存 |
| **合计** | **10 次/请求** | |

也就是说 **`mightContain` 内部 = 1 (`EXISTS`) + 7 (`GETBIT`) = 8 次**，占了整条跳转链路 10 次往返里的 **8 次**。

**问题**：7 个位是 7 次独立 `GETBIT` —— 在"往返即瓶颈"的本机环境里，这是单请求往返次数的大头。

**可选优化（两步，收益可叠加）**：

1. **`BITFIELD key GET u1 #off1 GET u1 #off2 ...`** 一条命令取回 7 位 —— **7 次 `GETBIT` → 1 次**，全链路 **10 → 4 次**。
   （Lua 脚本也行，但 `BITFIELD` 是原生命令、更短。代价是丢掉"提前返回" —— 但对**真码**来说本来就得取满 7 位，纯赚。）
2. 再把 `EXISTS BLOOM_READY` 用本地 `volatile` 缓存掉 → **4 → 3 次**。
   （代价：rebuild 期间本地状态与 Redis 短暂不一致 —— 但重建期本来就是"未就绪 → 放行"的语义，风险可控。）

**落地结果（已做，2026-10-12）**：第 1 步已实施并实测 —— `mightContain` 改用 `BITFIELD` 一次取回 7 位，全链路 **10 → 4 次/请求**（验收判据：`cmdstat_getbit:calls` **归零**、`cmdstat_bitfield:calls` ≈ 请求数）。

过程中炸出**两个连带缺陷**（都比优化本身值钱，都已修）：

- **不可变 API 误用**：`BitFieldSubCommands#get(...)` 返回**新实例**（不是往 `this` 里 add），丢弃返回值 → 7 个子命令全丢 → 真码全 404。证据是 `MONITOR` 抓到一条**光杆** `BITFIELD`。
- **隐式依赖 long 溢出**：原式 `i * indices[1]` 的乘积超 `Long.MAX` 回绕；写侧/读侧用同一套溢出结果所以"能工作"，但**跨语言复算会失配**（本次就因此一度得出"布隆只有 20% 完整"的假结论）。已改为内外都取模。

另补上**启动自动重建** —— `rebuildBloomFilter()` 原先**全库无任何调用者**，布隆一旦被清就永不恢复。

详见 `docs/05` 三之五十六（R106~R111）。

> 第 2 步（`EXISTS` 本地缓存）**暂不做**：多实例下"一台 rebuild、其他机器本地标志仍为 true"会不一致。
> ⚠️ 本次只验了**往返数**（`commandstats`），**QPS 影响尚未重跑**（见第十二节第 5 项）。

## 十、复现步骤

```bash
# 0. 起依赖（Docker Desktop 要先开）
cd short-link

# 1. 起应用（压 A/B 组时建议把限流放开，否则会被 429 挡住）
unset SERVER__PORT
mvn -o spring-boot:run -Dspring-boot.run.arguments="--short-link.limit-capacity=1000000 --short-link.limit-refill-rate=1000000"

# 2. 造数：3000 条真短链 + 3000 个无效码
java bench/GenCodes.java --mode random --count 3000 --out bench/invalid.txt
java bench/GenCodes.java --mode create --count 3000 --out bench/codes.txt

# 3. A 组：布隆开 / 关
redis-cli SET shortlink:bloom:ready 1                       # 开
bash bench/run-arm.sh A1-BLOOM-ON  bench/invalid.txt 50 loop 15 5
redis-cli DEL shortlink:bloom:ready                          # 关
bash bench/run-arm.sh A2-BLOOM-OFF bench/invalid.txt 50 loop 15 5

# 4. B 组：缓存冷 / 热（冷臂前先清 shortlink:code:*）
bash bench/run-arm.sh B1-COLD bench/codes.txt 50 once 15 0
bash bench/run-arm.sh B2-WARM bench/codes.txt 50 once 15 0

# 5. C/D 组：限流开 / 关 + 队列增长
bash bench/run-arm.sh C-OFF bench/codes.txt 100 loop 15 5
redis-cli LLEN shortlink:access:queue
```

> 注意：`once` 模式必须把 `warmup` 传 **0**，否则整轮都会被预热窗口滤掉（实测踩过：样本数 0、QPS 0）。

## 十三、复跑校验（2026-10-12）：一个被推翻的归因

§11 第 7 条曾把"绝对 QPS 只有 ~1170"归因于 `log-impl: StdOutImpl` 同步刷 stdout，并注明"数字待重跑刷新"。本次按第十节的复现步骤**完整重跑 A / B / C 三组**，结论是 —— **那个归因不成立**。

### 13.1 复跑结果（与原报告对照）

| 臂 | 原报告 QPS | 本次复跑 | 变化 | 该臂的 SQL 量 |
|---|---|---|---|---|
| A1 布隆开 | 1998 | **1315**（4 轮均值） | **−34%** | `Com_select = 3` ← **几乎没有 SQL** |
| A2 布隆关 | 1833 | **1082**（3 轮中位） | **−41%** | `Com_select ≈ 16000` |
| B1 缓存冷 | 940 | **860**（3 轮中位） | −8.5% | `Com_select = 3003` |
| B2 缓存热 | 1176 | **986**（3 轮中位） | −16% | `Com_select = 3` |
| C-OFF 限流关 | 1176 | **1025**（3 轮中位） | −13% | `Com_select = 3` |
| C-ON 限流开 | 1741 | **1387**（3 轮中位） | −20% | `Com_select = 3`；429 占 **99.28%** |

⭐ **所有臂都降了** —— 包括 `Com_select = 3`、**压根没有 SQL 日志可写**的 A1 / B2 / C。所以降幅只能来自**环境漂移**（同一台机器、同一份代码、同一批数据，隔一天复跑），而不是某次改动。

> 这也是**不能"拿新数字直接替换旧数字"**的原因：两组数字测于不同环境状态，混在一张表里反而不可比。**保留原数字 + 增加本节，比替换更诚实。**

### 13.2 对照实验：只切 `log-impl`，其余一律不动

要判断 `log-impl` 到底值多少，不能跨环境比，只能**同实例、单变量**：

```bash
# 无日志态（当前主配置，不带 log-impl）
mvn spring-boot:run -Dspring-boot.run.arguments="--short-link.limit-capacity=1000000 --short-link.limit-refill-rate=1000000"

# 有日志态：只把 log-impl 用启动参数加回来（不改任何文件）
mvn spring-boot:run -Dspring-boot.run.arguments="--short-link.limit-capacity=1000000 --short-link.limit-refill-rate=1000000 --mybatis-plus.configuration.log-impl=org.apache.ibatis.logging.stdout.StdOutImpl"
```

`log-impl` 是**配置项**，因此可以用启动参数单点覆盖 —— **不改代码、不改配置文件**，这是本次能做出干净对照的前提。

| 臂 | 无日志态 | 有日志态 | 差 |
|---|---|---|---|
| **A2**（布隆关） | **1082**（1082 / 1221 / 1030） | **1123**（1123 / 1142 / 975，前 2 轮预热丢弃） | **+3.8%** |
| **B1**（缓存冷） | **860**（964 / 860 / 845） | **944**（898 / 944 / 944） | **+9.8%** |

日志确实写出去了（否则实验无效）：

| 态 | `Preparing:` 行数 | 日志文件 | 对应 QPS |
|---|---|---|---|
| 无日志 | **0** | 18 MB | 1082 / 860 |
| **有日志** | **75,562** | **38 MB** | 1123 / 944 |

**读法**：

1. 两臂的差异（+3.8% / +9.8%）**都落在单臂自身的波动范围里**（A1 连跑 4 轮是 1140 ~ 1446，±12%）；
2. 更关键的是**方向不一致**：A2 是"有日志略快"、B1 也是"有日志略快" —— 若 `log-impl` 真是瓶颈，两臂都该"有日志明显更慢"；
3. 所以结论是：**`log-impl` 的代价低于测量噪声，测不出来。**

### 13.3 为什么它注定影响有限

| 原因 | 说明 |
|---|---|
| **它只作用于"有 SQL 的路径"** | 跳转的写侧本来就异步（D 组实测 `Com_insert = 0`）；只有 **A2（27509 次 SELECT）**、**B1（3003 次）** 会产生 SQL 日志 |
| **瓶颈在别处** | §八 的标定实验早就指出：并发 10 之后撞 ~1170 的天花板，**瓶颈是每请求 3~4 次 Redis 往返**（全走 Docker 端口转发，单次 ≈1.8 ms）。一次 `write` 系统调用（µs 级）与之差两个数量级 |
| **量级对不上** | 若 27509 行日志真能拖垮 A2，A2 就该显著慢于只有 3 行日志的 A1；但原报告 A2 = 1833 只比 A1 = 1998 低 8% —— **原报告内部本来就不自洽** |

### 13.4 顺带发现的两个测法问题

1. **`warmup` 只够单轮，不够"应用级"**：同一个臂连跑 4 轮，QPS 是 **1140 → 1397 → 1446 → 1275**。第一轮被"应用刚启动、C2 还没编译完"拖累，低 20%+。**跨臂对比要么全程同一实例，要么每个状态先空跑 2 轮丢掉**（已补进 §2.3 第 6 条）。
2. **"限流已关闭"这个措辞会误导**：`GET /{code}` 上挂着 `@RateLimit`，拦截器注册 `/**`，**没有任何开关能真正绕过它**。所谓"关闭"只是把 `cap/rate` 放大到 1000000 —— `EVALSHA` 照发（实测每请求仍是 `EVALSHA + EXISTS + BITFIELD` 三次往返）。§四 写"限流已关闭"，读者容易以为省了一次往返。

### 13.5 本节结论

| # | 结论 |
|---|---|
| 1 | **§11 第 7 条不成立**（`log-impl` 不是 QPS 天花板的直接原因），已就地订正；正确解释是 §八 的"Redis 往返次数" |
| 2 | A / B / C 三组的**相对关系全部保持成立** —— 布隆有效、缓存有效、限流有效。**本次复跑没有推翻任何一条优化结论** |
| 3 | 绝对 QPS 受环境漂移影响极大（同代码复跑可差 40%），**报告里的绝对数字只适合同批次内比较** |
| 4 | 把 `log-impl` 迁到 `application-dev.yml` 仍然是对的（本地要看 SQL、生产不该刷日志），**只是它的收益不在 QPS 上** |
| 5 | `BITFIELD`（10 → 4 次往返）的收益同样**没能在 QPS 上分离出来** —— 往返数是 `commandstats` 给的硬证据，而 QPS 被环境噪声淹没。**"计数器能看见、延迟看不见"再次成立**（§2.3 第 5 条） |
