## 一、起步七步（Day 1 一天做完）

| 步 | 动作 | 完成标志 |
|---|---|---|
| 1 | JDK / Maven / IDEA / Docker Desktop | `java -version` 能输出，且版本 ≥ 17（**本机是 25**，Boot 3.5 官方支持 17–25，够用；编译目标由 pom 的 `java.version=17` 决定） |
| 2 | 写 `docker-compose.yml`，起 MySQL 8 + Redis 7 | 能连上 `3306` 和 `6379` |
| 3 | 用 Spring Initializr 生成骨架 | 项目能正常 import 进 IDEA |
| 4 | 补齐依赖（见下表） | pom 里没有红色报错 |
| 5 | 配 `application.yml`（数据源 / Redis / MyBatis-Plus） | 启动日志无异常 |
| 6 | 把包结构建出来（**空包也先建**） | 目录树立起来 |
| 7 | 起服务，访问 `/actuator/health` | 返回 `UP` → 提交 Git，打 tag `v0.1` |

> ⚠️ **第 5 步做完之前，`mvn package` 一定会失败，这是正常的。**（2026-09-22 实测遇到）
>
> 骨架里自带一个 `ShortLinkApplicationTests`，它标了 `@SpringBootTest`，会尝试启动**整个** Spring 上下文。工程里一旦同时有了 MySQL 驱动和 MyBatis-Plus，自动配置就会去创建 `DataSource`；而此时 `application.properties` 里还没有 `spring.datasource.url`，于是：
>
> ```text
> Caused by: org.springframework.boot.autoconfigure.jdbc.DataSourceProperties$DataSourceBeanCreationException:
>     Failed to determine a suitable driver class
>   at ...DataSourceProperties.determineDriverClassName
> ```
>
> 三条要记住：
> 1. **这不是 pom 的问题**，是"环境还没搭完"。写完数据源配置之后，这条测试会自己变绿。
> 2. 在此之前要打包，就加参数：`mvn clean package -DskipTests`。
> 3. **别为了让它变绿而删掉这条测试。** 它是你的"环境就绪检测器"——它红 = 环境还没好。`-DskipTests` 是临时手段，不是习惯。
>
> 📌 另一个小坑：第 5 步要建的是 `application.yml`，那就把骨架里的 `application.properties` **删掉**。两个文件同时存在时 `.properties` 优先级更高，你改了 yml 却不生效，会排查很久。

> ✅ **反过来也要注意：`mvn test` 变绿 ≠ 环境真的通了。**（2026-09-22 实测确认）
>
> 两个原因叠加：① Spring Boot 对**解析不了的占位符是宽容的**——`password: ${MYSQL_PASSWORD}` 在环境变量缺失时会原样保留成字符串 `${MYSQL_PASSWORD}`，不报错；② Hikari 连接池是**懒连接**，测试期间根本不连库。
>
> 所以**最终验收只看 `/actuator/health`**：
>
> | 返回 | 含义 |
> |---|---|
> | `{"status":"UP"}` | db + redis 都连上了（任一组件 DOWN，整体就是 DOWN） |
> | `{"status":"DOWN"}` | 去日志里找 `Caused by`；密码错会报 `Access denied for user ...` |
>
> 默认看不到"哪个组件"，想看细节就在 **开发环境**加一行 `management.endpoint.health.show-details: always`（或 `show-components: always`），响应里就会多出 `components.db` / `components.redis`。
>
> ⚠️ `show-details: always` **只开在开发环境**——它会把数据库地址、版本这类信息暴露出去，线上要关掉（这正是第 5 步之外还要拆 `application-dev.yml` / `-prod.yml` 的理由之一）。

> 🔧 **让测试也能拿到配置（否则 `mvn test` 里连不上库）**（2026-09-22 实测踩到）
>
> 症状：应用跑起来 `/actuator/health` 是 UP，但一跑测试就报 `Access denied for user 'xxx'@'<ip>' (using password: YES)`。
> 原因：**IDE 里"跑应用"和"跑测试"是两套独立的运行配置**，给前者配的环境变量不会自动传给后者 → `${MYSQL_PASSWORD}` 没被解析，字面量字符串被当密码发给了 MySQL。
>
> 三种解法，推荐第 1 个：
> 1. **让 Spring Boot 自己读 `.env`**：在 `application.yml` 里加一行 `spring.config.import: optional:file:./.env[.properties]`。一份 `.env` 同时喂 Docker Compose 和 Spring Boot，IDEA / Maven / 命令行**任何方式启动都一致**，也不用再去配 IDE 环境变量（`optional:` 表示文件不存在也不报错）
> 2. 把环境变量配到 IDE 的**运行配置模板**上（Edit Configurations → Edit configuration templates），这样以后新建的运行配置都自带
> 3. 给占位符加默认值 `${MYSQL_PASSWORD:xxx}`——最省事，但等于把本地密码公开在仓库里
>
> 另一个坑：**冒烟测试里别用 `try/catch` 把异常吞掉**（只 `log.error` 不抛出）。测试框架看到"方法正常返回"就判成功——会出现"日志里一片红、测试却全绿、退出码 0"的假象。要断言，或者让异常直接抛出去。
>
> 还有：**冒烟测试要能重复跑**。给测试方法加 `@Transactional`（跑完自动回滚），否则第一条断言就可能撞上唯一索引（`short_code` / `origin_url_md5` 都是唯一键），第二次执行必然失败。

### 第 4 步：依赖清单

| 依赖 | 用途 |
|---|---|
| `spring-boot-starter-web` | Web 能力 |
| `spring-boot-starter-validation` | 参数校验（`@Valid`） |
| `spring-boot-starter-data-redis` | Redis（自带 Lettuce 客户端） |

| `springdoc-openapi-starter-webmvc-ui` | 接口文档底层（**版本必须手动指定**，见下方第二个大坑） |
| `lombok` | 少写样板代码 |

> **第一个大坑**：Spring Boot 3 全面改用 `jakarta.*` 命名空间。所以 MyBatis-Plus 和 Knife4j **必须选支持 Spring Boot 3 的 starter**（名字里带 `boot3` 或 `jakarta`）。选错了会启动报 `ClassNotFoundException` / `NoClassDefFoundError`，报错信息还很难懂。这一步卡住别硬扛，直接来问我。

> **第二个大坑（本项目已实测确认，2026-09-22）**：Knife4j 4.5.0 内部钉死的是 `springdoc-openapi 2.3.0`，而 Spring Boot 3.5 需要 springdoc **2.8.x**。这个坑最阴的地方是——**编译、打包、`mvn package` 全都成功**，只有真正启动后访问 `/doc.html` 才炸，控制台报：
>
> ```text
> NoSuchMethodError: 'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'
> ```
>
> 表现是文档页空白、接口列表出不来。**解法**：把 Knife4j 里那条 springdoc 依赖**排除掉**（`<exclusions>` 里写 `org.springdoc:springdoc-openapi-starter-webmvc-ui`），再把 `org.springdoc:springdoc-openapi-starter-webmvc-ui` 以 **2.8.x**（如 2.8.13）**显式**声明成一条独立依赖。想看当前实际版本，随时跑 `mvn dependency:tree -Dincludes=org.springdoc:*`。

> **第三个大坑（M2 阶段实测确认，2026-09-23）**：统一响应体 `Result` **一定要交给 Lombok 生成 getter，不要只写个构造方法**。
>
> 症状极隐蔽：`mvn package` 成功、应用正常启动、`/doc.html` 正常，但**所有接口都返回 HTTP 406**，响应体是空的，且日志里**一条业务异常都没有**。实际发生的事是：
>
> ```text
> WARN ... ExceptionHandlerExceptionResolver :
>   Failure in @ExceptionHandler GlobalExceptionHandler#handleException
> org.springframework.web.HttpMediaTypeNotAcceptableException: No acceptable representation
> ```
>
> 原因：Spring MVC 写响应体时走的是 Jackson，Jackson **靠 getter 找属性**。`Result` 如果只有 `private int code` 这类字段 + 一个全参构造器、没有 getter，Jackson 就认为"这个对象没有任何可序列化属性" → 抛 `HttpMediaTypeNotAcceptableException` → 406。
> 更迷惑的是：**连全局异常处理器本身也返回 `Result`**，所以它写响应时同样炸，异常被吞在 resolver 里，看起来像"异常处理器没生效"。
>
> **解法**：给 `Result` 加 `@Data`（或手写 getter）。类上加 `@Data` + `@NoArgsConstructor` 即可，静态工厂方法照常写。顺手加 `@JsonInclude(NON_NULL)`，`data` / `traceId` 为 null 时就不会出现在 JSON 里，响应体更干净。

> **第四个大坑（M2 阶段实测确认，2026-09-23）**：构造异常时把 message 传进 `super()`，处理器里**必须回头去读 `e.getMessage()`**，否则自定义提示会被静默丢弃。
>
> `BusinessException(ResultCode, String message)` 里写了 `super(message)`，但如果异常处理器统一 `return Result.fail(e.getResultCode())`，那就只取了枚举里的默认文案，**你传的 message 白写了**——而且不报错，只是前端看到的是"短码已被占用"而不是"短码 abc123 已被占用"。
>
> 正确姿势：处理器里判断 `e.getMessage()` 是否有内容 → 有就用它，没有就退回枚举默认值。校验异常同理——`MethodArgumentNotValidException` 能取到 `getBindingResult().getFieldErrors()`，`ConstraintViolationException` 能取到 `getConstraintViolations()`，把**第一条字段级提示**返回去，比笼统的"参数错误"有用得多。

## 三之二、M2 验收怎么测（不需要手动点）

验证统一返回 + 全局异常，有两条路，**推荐第 1 条**。

| 方式 | 怎么写 | 优点 | 缺点 |
|---|---|---|---|
| **1. MockMvc 自动化测试** | 测试类加 `@SpringBootTest` + `@AutoConfigureMockMvc`，注入 `MockMvc`，用 `mockMvc.perform(get(...))` 发请求 | 一键跑完 6 种场景；可断言 `jsonPath("$.code")`；**能进 CI**；肉眼看得到响应体 | 要写代码 |
| 2. curl 手工脚本 | 应用启动后 `curl -i` 打各个端点 | 零学习成本，最贴近真实调用 | 每改一次要重启、手点；无法回归 |

**MockMvc 断言四件套**：

```
.perform(get("/api/demo/ok"))                 ← 发请求（get/post 静态导入）
.andDo(print())                                ← 把请求 + 响应原样打到控制台，肉眼验收靠它
.andExpect(status().isOk())                    ← 断言 HTTP 状态码
.andExpect(jsonPath("$.code").value(0))        ← 断言响应体字段（jsonPath 是 JsonPath 语法）
```

要验的 **6 种场景**（一个 `@Test` 一个场景，方法名写清场景）：

| # | 场景 | 期望 HTTP | 期望 `code` |
|---|---|---|---|
| 1 | 正常成功 | 200 | 0 |
| 2 | 业务异常（主动抛） | 200 | 枚举里的码（如 40005） |
| 3 | 业务异常 + 自定义 message | 200 | 40006 且 message 是自定义的 |
| 4 | `@Valid @RequestBody` 校验失败 | 200 | 40001 |
| 5 | `@RequestParam` 校验失败 | 200 | 40001 |
| 6 | 兜底异常（故意造 NPE） | 200 | 50000，且 body 里**没有** `stackTrace` |

**错误码分段**（`ResultCode` 枚举）：`0` 成功 / `400xx` 客户端问题 / `500xx` 服务端问题。
**不要复用 HTTP 状态码当业务码** —— 业务码会越加越多（`40003` 短码格式非法、`40004` 过期时间非法都是 400 语义但要分开提示），同号很快不够用；而且同一个业务码在跳转接口是 410、在管理接口是 200，绑死会互相牵制。

**第 5 条有一个前置条件容易漏**：`@RequestParam` / `@PathVariable` 上的校验注解要生效，**Controller 类上必须加 `@Validated`**（`@Valid` 不够，那个只管 body）；方法级校验是靠 AOP 拦截器实现的，依赖 `spring-boot-starter-validation`。

**第 6 条的意义**：证明兜底处理器接住了未预期异常，且**没把堆栈泄露给前端**。断言里显式写 `jsonPath("$.stackTrace").doesNotExist()`，这就是"不暴露内部实现"那条要求的落地。

> ⚠️ **看到 HTTP 200 才是对的**。业务失败也返回 HTTP 200、靠 `code` 区分——这是本项目 `docs/03-接口设计.md` 定下的约定，MockMvc 里如果断言 `status().isBadRequest()` 反而会失败。**唯一例外**是跳转接口（302/410），它不走统一响应体。

> ⚠️ **测试文件别和业务测试混在一个类里。** demo 的测试单独放 `src/test/java/.../controller/DemoControllerTest.java`，M2 验收完整个删掉（`DemoController` + `DemoControllerTest` 一起删），不要留在仓库里当"示例代码"——面试官看到临时验证类会扣印象分。

### 校验注解为什么能"自动抛异常"？

这是 M2 阶段最容易懵的一点：`@NotBlank` / `@Pattern` 只是**声明式的注解**，方法体里明明没有 `if`，为什么设了 `@Valid` / `@Validated` 就真的会拦下请求、还会跳到全局异常处理器？

**因为拦请求的根本不是注解本身，而是 Spring 通过 AOP 加的一层拦截器。**

| 注解 | 挂在哪 | 谁在拦 | 抛出的异常 |
|---|---|---|---|
| `@Valid`（或 `@Validated`） | `@RequestBody` **参数**前 | `RequestResponseBodyMethodProcessor`（请求体反序列化时顺手校验） | `MethodArgumentNotValidException` |
| `@Validated` | **Controller 类**上 | `MethodValidationInterceptor`（AOP 切面，需 `spring-boot-starter-validation`） | `ConstraintViolationException` |

所以：

1. **注解是"配置"，拦截器是"执行者"。** 两个条件缺一不可——注解写了，但类上没 `@Validated`（或参数前没 `@Valid`），拦截器根本不会被触发，方法会**照常执行到底**，`@Pattern` 就是个装饰品。
2. **方法体里的 `return Result.success(code)` 永远不会被执行**。因为异常是在**进入方法体之前**抛出的——拦截器先校验，不通过就直接 `throw`，方法体压根没机会跑。
3. **这就是为什么测试会失败**：`return Result.success(...)` 那句写在那儿是"看起来会成功"，但校验失败的请求走不到它。测试断言 `code=0` 必然失败——**这正是"测试生效了"的证明**，不是测试写错了。
4. **异常不会漏出去**，因为全局异常处理器上有 `@ExceptionHandler(ConstraintViolationException.class)`，把它接住转成统一响应体返回。你在 MockMvc 里看到 HTTP 200 + `code=40001`，就是"拦下 → 抛出 → 接住 → 包装"这条链走通了。

> **验证方式**：把 Controller 类上的 `@Validated` 注释掉再跑用例 5——`code` 会变成 `0`（请求一路走到底、不校验），这就反证了"真正干活的是拦截器，不是注解"。

> **顺带一个坑**：方法级校验（`@RequestParam` / `@PathVariable` 上的注解）依赖 AOP 代理。所以**同类内部方法互相调用不会触发校验**（`this.xxx()` 绕过了代理），这是个经典陷阱。

## 三之三、`@Value` 不能注入 static 字段（M3 实测确认）

想把配置项（如短链域名）用在一个 `static` 工具方法里，最容易写出来的错误形式是：

```java
public class ShortLinkConverter {
    @Value("${app.short-domain}")      // ❌ 静默失效
    private static String prefixUrl;
}
```

**症状**：不报错、不警告、编译通过、启动正常——只是**值恒为 `null`**。
（我用探针测试实测过：反射读出来就是 `[null]`。）

**原因**：Spring 的字段注入（`@Value` / `@Autowired`）走的是**实例初始化**流程，而 `static` 字段属于**类**、不属于对象。Spring 压根没有"给某个类的静态字段赋值"这条路径。
**危险的是它失败了不吭声**——如果这个 `null` 后面参与字符串拼接，你会得到 `"nullaB3xK9"` 这种脏数据，而不是异常。

**两种正确写法**（推荐第一种）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 改成 `@Component` + 实例方法** | 类加 `@Component`，`@Value` 注到**实例字段**（或构造器参数），方法去掉 `static` | ✅ 推荐。符合 Spring 心智，可测试、可 mock |
| ② 保留静态，用 setter 注入 | 类加 `@Component`，写一个 `@Value` 标注的**非静态 setter**，在 setter 里给 `static` 字段赋值 | 能跑但绕，调用方仍当成静态用，隐藏了依赖关系 |

**更要记住的判断标准**：**"静态工具类"和"读配置"本身就是矛盾的**。
工具类（如 `Base62Util`、`Md5Util`）的特点是**无状态、无外部依赖**，所以才能静态；一旦它需要读配置，它就**有依赖了**，就该是个 Spring bean。这也是 `docs/05` 里 `common.util` 那行写着"无状态工具、**不依赖 Spring 容器**"的原因。

## 三之四、对象转换时最容易漏的空值（M3 实测确认）

`converter` 里做时间字段的 `parse` / `format` 时，**先问自己这个字段能不能为 NULL**。

| 方向 | 字段 | 能否为 null | 漏判的后果 |
|---|---|---|---|
| DTO → entity | `expireTime` | **能**（`docs/03`：不填为永久） | `LocalDateTime.parse(null, fmt)` → NPE |
| entity → VO | `expireTime` | **能**（`docs/02`：`DATETIME NULL DEFAULT NULL`，"NULL 表示永久有效"） | `null.format(fmt)` → NPE |
| entity → VO | `createTime` | 落库前是 null | 同上 |

两条解法：

1. **转之前判空**，null 就保持 null（`VO` 里对应的 `String` 也是 null，Jackson 靠 `@JsonInclude` 不输出）。
2. **顺序约束**：`createTime` / `updateTime` 由**数据库默认值**填（本项目约定，不做 Java 侧自动填充），所以 **`insert` 之后实体对象里才有值**。这意味着 —— **`entity → VO` 必须在落库成功之后做，不能先转再存**。这个顺序搞反了会拿到 null 的 `createTime`。



验证统一返回 + 全局异常，有两条路，**推荐第 1 条**。

| 方式 | 怎么写 | 优点 | 缺点 |
|---|---|---|---|
| **1. MockMvc 自动化测试** | 测试类加 `@SpringBootTest` + `@AutoConfigureMockMvc`，注入 `MockMvc`，用 `mockMvc.perform(get(...))` 发请求 | 一键跑完 6 种场景；可断言 `jsonPath("$.code")`；**能进 CI**；肉眼看得到响应体 | 要写代码 |
| 2. curl 手工脚本 | 应用启动后 `curl -i` 打各个端点 | 零学习成本，最贴近真实调用 | 每改一次要重启、手点；无法回归 |

**MockMvc 断言四件套**：

```
.perform(get("/api/demo/ok"))                 ← 发请求（get/post 静态导入）
.andDo(print())                                ← 把请求 + 响应原样打到控制台，肉眼验收靠它
.andExpect(status().isOk())                    ← 断言 HTTP 状态码
.andExpect(jsonPath("$.code").value(0))        ← 断言响应体字段（jsonPath 是 JsonPath 语法）
```

要验的 **6 种场景**（一个 `@Test` 一个场景，方法名写清场景）：

| # | 场景 | 期望 HTTP | 期望 `code` |
|---|---|---|---|
| 1 | 正常成功 | 200 | 0 |
| 2 | 业务异常（主动抛） | 200 | 枚举里的码（如 40005） |
| 3 | 业务异常 + 自定义 message | 200 | 40006 且 message 是自定义的 |
| 4 | `@Valid @RequestBody` 校验失败 | 200 | 40001 |
| 5 | `@RequestParam` 校验失败 | 200 | 40001 |
| 6 | 兜底异常（故意造 NPE） | 200 | 50000，且 body 里**没有** `stackTrace` |

**错误码分段**（`ResultCode` 枚举）：`0` 成功 / `400xx` 客户端问题 / `500xx` 服务端问题。
**不要复用 HTTP 状态码当业务码** —— 业务码会越加越多（`40003` 短码格式非法、`40004` 过期时间非法都是 400 语义但要分开提示），同号很快不够用；而且同一个业务码在跳转接口是 410、在管理接口是 200，绑死会互相牵制。

**第 5 条有一个前置条件容易漏**：`@RequestParam` / `@PathVariable` 上的校验注解要生效，**Controller 类上必须加 `@Validated`**（`@Valid` 不够，那个只管 body）；方法级校验是靠 AOP 拦截器实现的，依赖 `spring-boot-starter-validation`。

**第 6 条的意义**：证明兜底处理器接住了未预期异常，且**没把堆栈泄露给前端**。断言里显式写 `jsonPath("$.stackTrace").doesNotExist()`，这就是"不暴露内部实现"那条要求的落地。

> ⚠️ **看到 HTTP 200 才是对的**。业务失败也返回 HTTP 200、靠 `code` 区分——这是本项目 `docs/03-接口设计.md` 定下的约定，MockMvc 里如果断言 `status().isBadRequest()` 反而会失败。**唯一例外**是跳转接口（302/410），它不走统一响应体。

> ⚠️ **测试文件别和业务测试混在一个类里。** demo 的测试单独放 `src/test/java/.../controller/DemoControllerTest.java`，M2 验收完整个删掉（`DemoController` + `DemoControllerTest` 一起删），不要留在仓库里当"示例代码"——面试官看到临时验证类会扣印象分。

### 校验注解为什么能"自动抛异常"？

这是 M2 阶段最容易懵的一点：`@NotBlank` / `@Pattern` 只是**声明式的注解**，方法体里明明没有 `if`，为什么设了 `@Valid` / `@Validated` 就真的会拦下请求、还会跳到全局异常处理器？

**因为拦请求的根本不是注解本身，而是 Spring 通过 AOP 加的一层拦截器。**

| 注解 | 挂在哪 | 谁在拦 | 抛出的异常 |
|---|---|---|---|
| `@Valid`（或 `@Validated`） | `@RequestBody` **参数**前 | `RequestResponseBodyMethodProcessor`（请求体反序列化时顺手校验） | `MethodArgumentNotValidException` |
| `@Validated` | **Controller 类**上 | `MethodValidationInterceptor`（AOP 切面，需 `spring-boot-starter-validation`） | `ConstraintViolationException` |

所以：

1. **注解是"配置"，拦截器是"执行者"。** 两个条件缺一不可——注解写了，但类上没 `@Validated`（或参数前没 `@Valid`），拦截器根本不会被触发，方法会**照常执行到底**，`@Pattern` 就是个装饰品。
2. **方法体里的 `return Result.success(code)` 永远不会被执行**。因为异常是在**进入方法体之前**抛出的——拦截器先校验，不通过就直接 `throw`，方法体压根没机会跑。
3. **这就是为什么测试会失败**：`return Result.success(...)` 那句写在那儿是"看起来会成功"，但校验失败的请求走不到它。测试断言 `code=0` 必然失败——**这正是"测试生效了"的证明**，不是测试写错了。
4. **异常不会漏出去**，因为全局异常处理器上有 `@ExceptionHandler(ConstraintViolationException.class)`，把它接住转成统一响应体返回。你在 MockMvc 里看到 HTTP 200 + `code=40001`，就是"拦下 → 抛出 → 接住 → 包装"这条链走通了。

> **验证方式**：把 Controller 类上的 `@Validated` 注释掉再跑用例 5——`code` 会变成 `0`（请求一路走到底、不校验），这就反证了"真正干活的是拦截器，不是注解"。

> **顺带一个坑**：方法级校验（`@RequestParam` / `@PathVariable` 上的注解）依赖 AOP 代理。所以**同类内部方法互相调用不会触发校验**（`this.xxx()` 绕过了代理），这是个经典陷阱。

## 四、三条铁律（面试会问，现在就要养成习惯）

### 铁律 1：依赖只能单向向下

```
controller  →  service  →  mapper  →  DB
```

- ✅ `controller` 调 `service`，`service` 调 `mapper`
- ❌ `service` 里出现 `HttpServletRequest`
- ❌ `mapper` 里调 `service`
- ❌ `controller` 直接调 `mapper`（这一条最常见，也最致命）

**为什么**：一旦反向依赖，代码就无法复用、无法单测，后面加缓存、加限流时会发现改一处崩三处。

### 铁律 2：entity 不出业务层

`entity` 是数据库的样子，`vo` 是前端该看到的样子。二者**必须分开**。

原因很实际：`entity` 里有 `del_flag`、`origin_url_md5`、`seq_no` 这些字段，直接返回给前端等于**泄露内部实现**。而且哪天数据库加字段，接口就跟着变，前端会莫名其妙炸掉。

### 铁律 3：`common` 不许依赖任何业务包

`common` 是被所有人依赖的，它一旦依赖了 `service`，就形成循环依赖。

## 六、一次请求会穿过哪些包

以「创建短链」为例：

```
HTTP 请求
  → filter/TraceIdFilter          生成 traceId 放进 MDC
  → interceptor/RateLimitInterceptor  限流判断（W5 才有）
  → controller/ShortLinkController    参数校验 → 调 service
  → service/ShortLinkServiceImpl      业务编排：查重 → 发号 → 落库
  → mapper/ShortLinkMapper            SQL
  → MySQL / Redis
  → 逐层返回，converter 组装成 VO，包装成 Result
```

**看懂这条链路，你就知道每个包为什么存在。**

## 七、新手最容易犯的 6 个错

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | Controller 里写业务逻辑 | 无法复用、无法测试，加缓存时无从下手 | 全部下沉到 service |
| 2 | 直接把 entity 返回给前端 | 泄露 `delFlag` 等内部字段 | 转成 vo |
| 3 | Redis 用默认 JDK 序列化 | key/value 变成乱码二进制，排查时看不懂 | 在 `RedisConfig` 里配 String + JSON 序列化 |
| 4 | `@Transactional` 包住 Redis 调用 | 事务未提交缓存已写 → 脏数据 | 事务只管数据库，缓存操作放事务外 |
| 5 | 所有类堆在 controller 一个大包里 | 工程没有结构，简历上不好看 | 按上面的包结构分 |
| 6 | 只在 Controller 校验参数 | 内部调用绕过校验 | DTO 校验 + service 层再兜一次 |
