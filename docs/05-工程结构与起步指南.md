# 工程结构与起步指南

> 这份文档解决一个问题：**从零到能跑，中间有哪些动作；代码该放在哪个包里。**
> 只讲结构和边界，不写具体代码。

## 一、起步七步（Day 1 一天做完）

| 步 | 动作 | 完成标志 |
|---|---|---|
| 1 | 装 JDK 17 / Maven / IDEA / Docker Desktop | `java -version` 显示 17 |
| 2 | 写 `docker-compose.yml`，起 MySQL 8 + Redis 7 | 能连上 `3306` 和 `6379` |
| 3 | 用 Spring Initializr 生成骨架 | 项目能正常 import 进 IDEA |
| 4 | 补齐依赖（见下表） | pom 里没有红色报错 |
| 5 | 配 `application.yml`（数据源 / Redis / MyBatis-Plus） | 启动日志无异常 |
| 6 | 把包结构建出来（**空包也先建**） | 目录树立起来 |
| 7 | 起服务，访问 `/actuator/health` | 返回 `UP` → 提交 Git，打 tag `v0.1` |

### 第 3 步：Spring Initializr 怎么选

| 项 | 选择 |
|---|---|
| Project / Language | Maven / Java |
| Spring Boot | **3.5.x**（最新稳定版） |
| Group | `com.你的名字`（别用 `com.example`，简历上难看） |
| Artifact | `short-link` |
| Packaging / Java | Jar / **17** |
| 勾选依赖 | Spring Web、Validation、Spring Data Redis、Spring Boot Actuator、Lombok、MySQL Driver |

**MyBatis-Plus 和 Knife4j 不在 Initializr 的列表里，要手动加到 pom。**

### 第 4 步：依赖清单

| 依赖 | 用途 |
|---|---|
| `spring-boot-starter-web` | Web 能力 |
| `spring-boot-starter-validation` | 参数校验（`@Valid`） |
| `spring-boot-starter-data-redis` | Redis（自带 Lettuce 客户端） |
| `spring-boot-starter-actuator` | 健康检查、监控端点 |
| `mybatis-plus-spring-boot3-starter` | ORM |
| `mysql-connector-j` | MySQL 驱动 |
| `knife4j-openapi3-jakarta-spring-boot-starter` | 接口文档 |
| `springdoc-openapi-starter-webmvc-ui` | 接口文档底层（**版本必须手动指定**，见下方第二个大坑） |
| `lombok` | 少写样板代码 |

> **第一个大坑**：Spring Boot 3 全面改用 `jakarta.*` 命名空间。所以 MyBatis-Plus 和 Knife4j **必须选支持 Spring Boot 3 的 starter**（名字里带 `boot3` 或 `jakarta`）。选错了会启动报 `ClassNotFoundException` / `NoClassDefFoundError`，报错信息还很难懂。这一步卡住别硬扛，直接来问我。

> **第二个大坑（本项目已实测确认，2026-09-22）**：Knife4j 4.5.0 内部钉死的是 `springdoc-openapi 2.3.0`，而 Spring Boot 3.5 需要 springdoc **2.8.x**。这个坑最阴的地方是——**编译、打包、`mvn package` 全都成功**，只有真正启动后访问 `/doc.html` 才炸，控制台报：
>
> ```text
> NoSuchMethodError: 'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'
> ```
>
> 表现是文档页空白、接口列表出不来。**解法**：把 Knife4j 里那条 springdoc 依赖**排除掉**（`<exclusions>` 里写 `org.springdoc:springdoc-openapi-starter-webmvc-ui`），再把 `org.springdoc:springdoc-openapi-starter-webmvc-ui` 以 **2.8.x**（如 2.8.13）**显式**声明成一条独立依赖。想看当前实际版本，随时跑 `mvn dependency:tree -Dincludes=org.springdoc:*`。

## 二、包结构总览

```text
com.yourname.shortlink
├── ShortLinkApplication.java          启动类
│
├── common/                            【通用基础设施】不依赖任何业务代码
│   ├── result/                        Result、PageResult、ResultCode
│   ├── exception/                     BusinessException、GlobalExceptionHandler、ErrorCode
│   ├── constant/                      RedisKeyConstant、CommonConstant
│   ├── enums/                         LinkStatusEnum
│   └── util/                          Base62Util、Md5Util、IpUtil
│
├── config/                            【配置层】
│   ├── MybatisPlusConfig              分页插件、字段自动填充
│   ├── RedisConfig                    RedisTemplate 序列化（★ 必须自定义）
│   ├── WebConfig                      跨域、拦截器注册
│   ├── Knife4jConfig                  接口文档分组
│   └── ThreadPoolConfig               异步线程池
│
├── controller/                        【接口层】只做校验与组装
│   ├── ShortLinkController            创建 / 详情 / 分页 / 改状态 / 删除
│   ├── RedirectController             跳转（注意：不带 /api 前缀）
│   └── StatsController                统计查询
│
├── service/                           【业务层】业务逻辑与事务边界
│   ├── ShortLinkService
│   ├── StatsService
│   ├── BloomFilterService
│   ├── RateLimitService
│   └── impl/                          实现类
│
├── mapper/                            【数据访问层】只有 SQL
│   ├── ShortLinkMapper
│   ├── LinkAccessLogMapper
│   └── LinkStatsDailyMapper
│
├── entity/                            【数据库实体】与表一一对应
├── dto/                               【入参对象】ShortLinkCreateDTO …
├── vo/                                【出参对象】ShortLinkVO、LinkStatsVO …
├── converter/                         【对象转换】entity ↔ dto / vo
├── handler/                           MyMetaObjectHandler（自动填充时间字段）
├── interceptor/                       RateLimitInterceptor（限流）
├── filter/                            TraceIdFilter（traceId 注入 MDC）
└── job/                               【定时任务】统计聚合 / 布隆重建 / 缓存预热
```

> `resources` 下还要有 `mapper/*.xml`（如果你写 XML 版 SQL）。

## 三、每个包放什么（重点）

| 包 | 职责 | 该放 | **不该放** | 什么时候建 |
|---|---|---|---|---|
| `common.result` | 统一响应 | `Result<T>`、`PageResult<T>` | 业务枚举值 | W1 |
| `common.exception` | 异常体系 | `BusinessException`、全局异常处理器 | 业务判断逻辑 | W1 |
| `common.util` | 无状态工具 | `Base62Util`、`Md5Util` | 依赖 Spring 容器的类 | W1 |
| `config` | 装配与配置 | 各类 `@Configuration` | 业务逻辑 | W1 |
| `controller` | 接收请求 | 参数校验、调 service、组装返回 | **任何业务逻辑、直接调 mapper** | W1 |
| `service` | 业务逻辑 | 事务边界、缓存编排、跨表操作 | `HttpServletRequest`、返回 `Result` | W1 |
| `mapper` | 数据访问 | SQL、单表 CRUD | **业务判断、事务** | W1 |
| `entity` | 数据库映射 | 与表字段一致的属性 | 对外暴露、加业务方法 | W1 |
| `dto` | 入参 | 请求字段 + 校验注解 | 数据库字段（如 `del_flag`） | W1 |
| `vo` | 出参 | 前端需要的字段 | 敏感字段（如 `delFlag`、`originUrlMd5`） | W1 |
| `converter` | 对象转换 | `entity ↔ dto/vo` 的映射 | 业务逻辑 | W1 |
| `handler` | 框架回填 | `MetaObjectHandler` 自动填充时间 | 业务逻辑 | W1 |
| `interceptor` | 请求拦截 | 限流、登录校验 | 业务逻辑 | W5 |
| `filter` | 请求预处理 | traceId 注入、编码 | 业务逻辑 | W7 |
| `job` | 定时任务 | 统计聚合、布隆重建、缓存预热 | 被 Controller 直接调用 | W3 |

## 四、三条铁律（面试会问，现在就要养成习惯）

### 铁律 1：依赖只能单向向下

```
controller  →  service  →  mapper  →  DB
```

- ✅ `controller` 调 `service`，`service` 调 `mapper`
- ❌ `service` 里出现 `HttpServletRequest`
- ❌ `mapper` 里调 `service`
- ❌ `controller` 直接调 `mapper`（这一条最常见，也最致命）

**为什么**：一旦反向依赖，代码就无法复用、无法单测，后面加缓存、加限流时会发现改一处崩三处。

### 铁律 2：entity 不出业务层

`entity` 是数据库的样子，`vo` 是前端该看到的样子。二者**必须分开**。

原因很实际：`entity` 里有 `del_flag`、`origin_url_md5`、`seq_no` 这些字段，直接返回给前端等于**泄露内部实现**。而且哪天数据库加字段，接口就跟着变，前端会莫名其妙炸掉。

### 铁律 3：`common` 不许依赖任何业务包

`common` 是被所有人依赖的，它一旦依赖了 `service`，就形成循环依赖。

## 五、配置文件怎么分

| 文件 | 放什么 |
|---|---|
| `application.yml` | 公共配置 + `spring.profiles.active` |
| `application-dev.yml` | 本地：数据源、Redis 地址、日志级别 DEBUG |
| `application-prod.yml` | 服务器：连接池参数、日志级别 INFO |

**要点**：数据库密码等敏感信息用**环境变量**占位，不要直接写死在文件里（简历和 GitHub 上都会被看到）。

## 六、一次请求会穿过哪些包

以「创建短链」为例：

```
HTTP 请求
  → filter/TraceIdFilter          生成 traceId 放进 MDC
  → interceptor/RateLimitInterceptor  限流判断（W5 才有）
  → controller/ShortLinkController    参数校验 → 调 service
  → service/ShortLinkServiceImpl      业务编排：查重 → 发号 → 落库
  → mapper/ShortLinkMapper            SQL
  → MySQL / Redis
  → 逐层返回，converter 组装成 VO，包装成 Result
```

**看懂这条链路，你就知道每个包为什么存在。**

## 七、新手最容易犯的 6 个错

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | Controller 里写业务逻辑 | 无法复用、无法测试，加缓存时无从下手 | 全部下沉到 service |
| 2 | 直接把 entity 返回给前端 | 泄露 `delFlag` 等内部字段 | 转成 vo |
| 3 | Redis 用默认 JDK 序列化 | key/value 变成乱码二进制，排查时看不懂 | 在 `RedisConfig` 里配 String + JSON 序列化 |
| 4 | `@Transactional` 包住 Redis 调用 | 事务未提交缓存已写 → 脏数据 | 事务只管数据库，缓存操作放事务外 |
| 5 | 所有类堆在 controller 一个大包里 | 工程没有结构，简历上不好看 | 按上面的包结构分 |
| 6 | 只在 Controller 校验参数 | 内部调用绕过校验 | DTO 校验 + service 层再兜一次 |

## 八、方向线路（包结构 ↔ 8 周计划）

| 阶段 | 新增 / 激活的包 | 做什么 |
|---|---|---|
| **W1** | `common` `config` `controller` `service` `mapper` `entity` `dto` `vo` `converter` `handler` | 骨架 + 创建短链接口 |
| **W2** | `service`（缓存逻辑）、`RedirectController`、`RedisConfig` | 跳转 + 缓存三大问题落地 |
| **W3** | `BloomFilterService`、`job`（缓存预热） | 布隆过滤器 |
| **W4** | `job`（统计聚合）、`ThreadPoolConfig`、`StatsController` | 异步统计 |
| **W5** | `interceptor`（限流）、`RateLimitService` | Lua 限流 |
| **W6** | **不新增包** | 只做压测与优化 |
| **W7** | `filter`（traceId）、异常处理完善 | 可观测性 |
| **W8** | — | Docker 部署 |

> **注意 W6**：那一周不许新增功能，只优化。这是纪律——很多人的项目烂尾，就是因为永远在加新东西，从不回头打磨。
