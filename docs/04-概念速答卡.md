## 一、短码生成

**Q：你的短码是怎么生成的？**

Redis `INCR shortlink:seq` 拿全局自增序号，再 Base62 编码成短码。选它的原因是**绝对唯一、无冲突、不需要查重**；Redis 单线程执行 `INCR` 天然原子，单机十万级 QPS。

**Q：为什么不用数据库自增 ID 当短码？**

两个原因：
1. **可枚举** —— 别人把 ID 从 1 递增就能遍历你全部短链，私密链接直接泄露；
2. **暴露业务量** —— 竞对看 ID 增速就知道你每天新增多少条。

**Q：那用随机短码呢？**

随机会冲突，每次生成都要查重，而且冲突概率随存量上升（生日悖论）。适合量小、对性能不敏感的场景。

**Q：直接对长链做哈希呢？**

哈希（如 MD5 取前 6 位）**天然幂等**——同一条长链永远得到同一个短码，不用查重。但它会碰撞；一旦碰撞就得加盐重试，而加盐又破坏了幂等性。

**这就是"哈希派"和"发号派"的本质取舍**：哈希拿幂等换冲突，发号拿可预测换零冲突。

**Q：Base62 是什么？**

字符表 `0-9a-zA-Z` 共 62 个字符。把十进制序号按 62 进制展开即可。

例：序号 `12345678` = 51×62³ + 49×62² + 41×62¹ + 52 → 查表得 `PFNQ`。

**Q：Redis 挂了发不了号怎么办？**

**号段模式**：一次从 DB 取 `step` 个序号（如 1000 个）缓存在内存里逐个发，DB 访问量降到 1/1000。代价是服务重启会浪费剩余号段、多实例之间序号不连续——这两个代价都可接受。

**Q：你的短码能被猜出来吗？**（诚实答法）

**能。** 自增发号本质上就是**可预测**的 —— 短码 = 在固定偏移 `62^5 = 916132832` 上做**标准 Base62 编码**，于是 `seq=1 → 100001`、`seq=2 → 100002`、`seq=3 → 100003`……**连号**。

⚠️ **这和"为什么不用数据库自增 ID"是同一个弱点的同一侧** —— 那边答"可枚举"，这边其实也**可枚举**，只是把起点推后了 6 位。所以**别答"我做了混淆"**（代码里没有打乱字符表，`BASE62_CHARS` 是标准序）。

要强防枚举，我会换成**随机码 + 布隆过滤器去重**（或"发号 + 可逆加密"），代价是发号从"零冲突"变成"要处理冲突"、外加一次判重。短链业务我判断不值得 —— **短码不是凭证**。

## 二、幂等与并发兜底

**Q：同一条长链提交两次会怎样？**

返回同一个短码。做法：对长链取 MD5 建**唯一索引**，先查后插。

**Q：先查后插在并发下不就失效了？**

会失效。两个线程可能同时查到"不存在"，然后都去插入。

所以最终一致性靠**数据库唯一索引**兜底：后到的 INSERT 被拒绝，代码捕获 `DuplicateKeyException`，**重新查询**并返回已存在的短码。

**Q：为什么不在应用层加锁？**

- 单机加 `synchronized` / 本地锁 → 多实例部署就失效；
- 上分布式锁（Redis）→ 引入额外依赖和网络开销。

**唯一索引是零成本的强一致保证**，能用它就别用锁。

**Q：这算什么一致性？**

最终一致性。允许一次无效的 INSERT 尝试，但保证结果唯一。

## 三、302 vs 301

**Q：跳转为什么用 302 不用 301？**

301 是**永久重定向**，会被浏览器长期缓存，后果有两个：

1. 第二次访问**不再请求服务器** → 访问量统计全部丢失；
2. 跳转目标**再也改不了**（用户浏览器永远用旧的）。

302 是**临时重定向**，每次都回源，能统计也能改。

**Q：那 301 用在哪？**

确定永不变更的目标，比如网站换域名。短链天生要变，所以必须 302。

**Q：307 / 308 呢？**

它们的区别是**是否允许改变请求方法**：301/302 历史上允许把 POST 改成 GET，307/308 禁止。短链只用 GET，所以 302 足够。

## 五、缓存三大问题（W2）

### 0. 先记住区分方法

三大问题只看两件事：**数据存不存在** + **失效范围有多大**。

| 问题 | 数据在 DB 里存在吗 | 出问题的范围 | DB 承受什么 |
|---|---|---|---|
| **穿透** | **不存在** | 每一个请求都穿透 | 持续的无效流量 |
| **击穿** | 存在 | **单个热点 key** 过期 | 瞬时并发尖峰 |
| **雪崩** | 存在 | **一大批 key** 同时失效，或 Redis 整体宕机 | 全部流量 |

口诀：**穿透是"查了不存在的"，击穿是"一个过期"，雪崩是"一片过期 / 缓存挂了"。**

三者都会让请求绕过缓存直接打到 DB，所以解法是同一类思路：**在到达 DB 之前拦掉，或者让 DB 一次只承受一点。**

### 1. 穿透

**现象**：查询一个缓存和 DB 里**都不存在**的数据。缓存永远不命中，每次请求都打到 DB。

**为什么会发生**：恶意攻击（用不存在的 ID 高频刷接口）、爬虫、程序 bug 传了无效参数。

**解法（三层叠加，不是三选一）**

| 层次 | 做法 | 说明 |
|---|---|---|
| 最外层 | **参数校验** | 短码格式（长度、字符集）不对直接拒，连缓存都不查 |
| 中间层 | **布隆过滤器** | 所有存在的短码灌进布隆；说"不存在" → 直接 404 |
| 最内层 | **缓存空值** | DB 查不到也往缓存写占位符（`NULL`），TTL 设短（30-60 秒） |

**缓存空值的代价**：占额外内存；若攻击者用大量**不同**的不存在 key 来打，内存会涨。所以它只能兜底，**主力是布隆过滤器**。

### 2. 击穿

**现象**：某个**热点 key**（被疯狂访问的那个短链）刚好过期的一瞬间，所有并发请求同时发现缓存没了，全部涌向 DB。

**关键**：只有一个 key，但它是热点，并发量极大。

**解法**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **互斥锁** | 未命中时先抢分布式锁，抢到的去查 DB 重建缓存，其他线程短暂等待后重试 | 简单，DB 只被一个线程打 | 等待会阻塞；要处理锁超时与死锁 |
| **逻辑过期** | value 里带"逻辑过期时间"，物理上不设 TTL。读到逻辑过期 → **先返回旧值**，再异步起线程更新缓存 | 不阻塞，请求永远有响应 | 短时间内返回旧数据 |
| 热点永不过期 | 后台定时任务刷新 | 简单 | 要维护热点名单 |

**本项目的推荐：逻辑过期。** 因为短链的 `origin_url` 生成后不再改动，即使返回"旧值"也完全正确。这是个很加分的答法。

### 3. 雪崩

**现象**：一大批 key 在**同一时刻失效**，或 **Redis 整体挂掉**，所有请求一起打到 DB，DB 被打死。

**为什么会同时失效**：最常见的根因是——所有 key 都是同一时间写入的，且 TTL 都设了同一个值（比如统一 24 小时），于是它们也会在同一时间集体过期。

**解法**

| 方案 | 做法 |
|---|---|
| **TTL 加随机抖动** | `ttl = 86400 + Random(0, 600)`，把失效时间打散。**最核心的一招** |
| 多级缓存 | 本地缓存（Caffeine）+ Redis，Redis 挂了本地还能顶一阵 |
| Redis 高可用 | 哨兵 / 集群，消除单点 |
| 熔断降级 | 缓存不可用时在 DB 前限流，或直接返回"系统繁忙"，保护 DB 不被拖死 |
| 缓存预热 | 服务启动时把热点数据先加载进缓存 |

## 六、布隆过滤器（W3）

**Q：布隆过滤器是什么？**

一个**超长 bit 数组** + **k 个不同的哈希函数**。用来快速判断某个元素**一定不存在**。

**Q：怎么工作？**

- **添加**元素：用 k 个哈希函数算出 k 个位置，全部置 1。
- **查询**元素：
  - 只要有**任意一位是 0** → **一定不存在**
  - k 位**全是 1** → **可能存在**（也可能是别的元素把它置 1 的）

**Q：核心特性？**

**没有假阴性，只有假阳性。** 说"不存在"→ 一定不存在；说"存在"→ 不一定存在。

**Q：为什么不能删除元素？**

多个元素共享 bit 位，把某一位清 0 会误伤其他元素。要支持删除得用 **Counting Bloom Filter**（用计数器代替单个 bit）。

**Q：误判率怎么控制？**

取决于三个量：bit 数组长度 `m`、元素个数 `n`、哈希函数个数 `k`。取 `k ≈ (m/n)·ln2` 时误判率最低，工程上通常能压到 1% 以内。

**Q：在短链项目里怎么用？**

1. 启动时 / 定时任务把 `t_short_link` 里所有 `short_code` 灌进布隆；
2. 跳转请求先问布隆：
   - 说**不存在** → 直接 404（连 Redis 都不查，从源头挡掉穿透）；
   - 说**可能存在** → 走正常的 Redis → MySQL 流程；
3. 新建短码时同步 `add` 进布隆。

**Q：有哪些实现方式？**

| 实现 | 形态 | 适用 |
|---|---|---|
| **手写 Redis Bitmap**（`SETBIT` / `GETBIT` / `BITCOUNT`） | 分布式 | **推荐** —— 教学价值最高，面试最能讲 |
| Guava `BloomFilter` | 本地内存 | 单机最快跑通 |
| Redisson `RBloomFilter` | 分布式 | 开箱即用 |

**Q：布隆过滤器的局限？**

- 只能拦"本来就不存在"的 key，**不能替代缓存**；
- 只解决**穿透**，解决不了击穿和雪崩；
- 元素只能加不能删（除非用 Counting 版）。

## 七、缓存与 DB 一致性（W2）

**Q：缓存和数据库怎么保证一致？**

Cache-Aside（旁路缓存）模式：**读**先查缓存，miss 回源查库并回填；**写**先更新库、**再删缓存**（不是更新缓存）。

**Q：为什么是"删缓存"而不是"更新缓存"？**

- 两个并发写请求的到达顺序不可控，更新缓存容易把旧值写进去；**删是幂等的**，谁先谁后都不影响结果；
- 缓存是"用到才回填"，删掉的代价只是下一次读多一次回源。

**Q：为什么"先更库、再删缓存"？反过来行不行？**

反过来（先删缓存、再更库）有个固定漏洞：① A 删缓存 → ② B 读 miss、回源读到**旧值** → ③ B 把旧值回填 → ④ A 才更新库。结果是**缓存是旧值、库是新值**，且这个旧值会一直活到 TTL 过期。

**Q：延迟双删是什么？**

先删缓存 → 更库 → 睡一小会儿 → **再删一次**。第二次删是为了兜住"第一次删之后、更库提交之前"被回填进去的旧值。代价是要**估算睡眠时间**，治不了根本问题。

**Q：本项目里为什么连"删缓存"都不用？**

短链的 `origin_url` **生成后不再修改** → 没有"更新"路径，只有"创建"和"删除"。创建时不写缓存（懒加载回填就行）；删除时也不需要 `DEL` —— 因为 **TTL 设计保证了缓存会比数据库记录先消失**（见下一条）。

**Q：TTL 怎么算的？为什么它这么关键？**

`calcTtlSeconds` 分两种：

| 情况 | 公式 |
|---|---|
| 永不过期的链接 | `基准(86400) + 抖动(≤3600)` |
| 有 `expire_time` 的链接 | `max( min(基准, 剩余寿命) - 抖动, 1 )` |

三个要素缺一不可：

| 要素 | 不做会怎样 |
|---|---|
| ① 有基准（24h） | 大量 key 只有几分钟寿命，缓存形同虚设 |
| ② `min(基准, 剩余寿命)` **硬上限** | 缓存会**活过 `expire_time`** → 同一短码两种状态码（清理任务软删后：缓存答 410、查库答 404） |
| ③ 抖动**只许提前** + 下限 1s | 加过头同上；减到 ≤0 会抛 `ERR invalid expire time` |

> **② 是"清理任务不需要反向删缓存"这句结论的唯一前提** —— 因为 TTL 永远 ≤ 剩余寿命，缓存必然比库里的记录先消失。

**Q：缓存里存"快照"还是"结论"？**

存**记录快照**（`originUrl` / `status` / `expireTime` 三个字段），不是存一个 `REUSABLE`/`EXPIRED` 的字符串 —— 这样命中缓存后**不需要再查库**就能重新判定。

配套铁律：**判定逻辑必须单源**。缓存路径和查库路径调**同一个** `classify(status, expireTime)` —— 否则"两份内容相同的判断，改一处忘一处就是 bug"（同一个短码，走缓存说可用、走库说禁用）。

**Q：Redis 挂了跳转怎么办？**

**降级回源 MySQL，仍返 302**（只是变慢）。这是 **fail-open**：缓存是加速层，不该让功能不可用。实测 `docker pause` Redis 后单请求 3.0s；加了"本次读缓存失败"标志后，省掉 `set` 那次超时（`timeout` 后来从 3s 调到 500ms）。

## 八、异步削峰：访问日志（W4）

**Q：访问日志为什么不直接写库？**

跳转是全系统 QPS 最高的接口，W2/W3 的全部努力就是让它**不碰 MySQL**。同步 `INSERT` 一行明细 = **给最热的读接口加一次写放大**，前面全白做。

所以把"写"整个挪出跳转链路：跳转线程只做一次 `RPUSH`（亚毫秒），`@Scheduled` 线程批量落库。

**Q：这样会丢数据吗？——先定档位**

| 档位 | 语义 | 落点 | 跳转代价 |
|---|---|---|---|
| 强不丢 | 每次访问必须落盘 | 同步 INSERT / WAL `fsync` | 一次 DB 往返 |
| **准不丢** ✅ | 进程崩、正常停机不丢；**断电最多丢 1 秒** | Redis List（开 AOF）`RPUSH` | 一次 Redis 亚毫秒往返 |
| 弱不丢 | 重启丢内存里没 flush 的 | JVM 有界队列 | 入队纳秒级 |

判据：**能不能接受"极少数情况丢一秒钟的量"？** 访问统计是近似值、按天可累加 → 准不丢足够，强不丢是过度设计。

**Q：为什么不加 `@EnableAsync`？**

因为这里的异步是 **`@Scheduled` 提供的**：入队由跳转线程自己 `RPUSH`、搬运由定时任务线程做，**两个环节都不需要线程池**。

**先加开关、以后再找消费者是反的** —— 一个没有消费者的 `@EnableAsync` 比不加更差（后人会以为"这里已经异步了"）。

**Q：怎么做到"不丢"？**

搬运端：**先提交事务、再删队列**。

```
flush() 去掉 @Transactional
→ TransactionTemplate 只包入库 saveBatch
→ execute 返回【之后】才 LTRIM
```

因为 Redis 和 MySQL **不在同一个事务里**：一旦"删队列"早于"提交成功"、提交又失败，数据就**真丢了**。反过来最坏是"重复搬一次" → 所以语义是**至少一次**。

> 注意：写在 `@Transactional` 方法体里面 ≠ 在事务之外，它只是"在提交之前" —— 这两件事完全不同。

**Q：最反直觉的一条结论？**

**客户端读超时 ≠ 服务端没执行。** `docker pause` 掉 Redis 后跳转报了"Redis 连接异常"，但 unpause 之后那条访问记录**照样出现** —— 因为 `RPUSH` 早已写进内核缓冲区，Redis 恢复后执行了它，只是当时的回复没人收。

推论：读超时是"**结果未知**"，不是"失败"。对访问明细无害（最多多记一条）；但对**扣款/扣库存**就是资损 —— 那类操作**必须有幂等键/唯一约束兜底**。

**Q：队列会无限涨吗？**

会 —— 这是压测炸出来的真问题。Redis 配置是 `maxmemory=0 + noeviction` → 队列无界增长的终点不是"报错"，而是**Redis 进程被 OOM Killer 干掉**，缓存/布隆/限流/队列**一起失效**。

两步修：

1. **提消费速率** —— 消费速率 = `批量 × 频率 ÷ 周期`，靠把 cron 从 5 分钟改成 1 分钟，从 66.7 提到 **333 条/秒**；
2. **给队列封顶** —— `LTRIM key -N -1` 保留最后 N 条，**丢最老的**。

> 丢老不丢新：下游最常问的是"最近一段"。丢最老 → "今天有数据" ✅；丢最新 → "今天全空" ❌。
> **给任何"生产者可能长期快于消费者"的缓冲区，都要同时回答：容量上限是多少、超限时丢什么。**

## 九、接口限流：令牌桶 + Lua（W5）

**Q：给哪个接口限流？为什么？**

跳转 `GET /{code}`。它是最高频、**无鉴权**、最易被刷的接口，也是整条链路的入口 —— 给它加限流 = **保护它下游的一切**。

**Q：限流维度怎么定？key 怎么拼？**

**IP + 路由模板**：`shortlink:limit:redirect:1.2.3.4`。

- 跳转无登录态 → "用户"维度用不了；
- 只按 IP 会和别的接口共用一个桶 → 误伤；
- **必须用"路由模板"（`redirect`）而不是真实 URI（`/aB3xY`）** —— 否则每个短码一个桶，**换着短码刷永远触发不了限流**。

**Q：为什么用令牌桶？**

防的是"**持续刷**"不是"手快两下"。`rate` 决定长期平均速率、`capacity` 决定允许的突发。内存 O(1)、误伤最小。

**Q：为什么这里必须用 Lua？**

这是全项目**第一个"读-算-写"非原子就出错的场景**。补令牌是四步：读 `tokens` → 按流逝时间补 → 判断 → 写回。若拆成多条命令，两个请求同时读到 `tokens=1` → **都放行 → 超发**。

对比 W2~W4：那些 Redis 用法全是"单条命令就够"（`SET` / `GETBIT` / `RPUSH`），天然原子，**不需要 Lua**。

**Q：限流怎么返回？为什么不能返 200？**

**`HTTP 429` + `Retry-After` + body `{"code":40009}`**。三条要点：

- **不能返 200** —— 限流是框架层拦截、不是业务失败；返 200 会让刷子在监控里"**隐形**"；
- **不能抛 `BusinessException`** —— 那会走 `handleBusinessException` 返回 200，429 失效；
- 在拦截器里直接 `setStatus(429)` + 用 `objectMapper` 序列化 `Result` 写 body（**不手写 JSON**，否则给 `Result` 的形状造第二处真相）。

**Q：Redis 挂了限流怎么办？**

**fail-open（放行）**。判据是"**这个依赖有没有替代路径**"：Redis 挂 → 放行 → 全站仍可用；若抛异常，每个跳转都 500，比"限流暂时失效"糟得多。

⚠️ **同一个异常，在"启动期"和"运行期"处置相反**：启动自检遇到**确定性**错误（脚本语法错）该**抛**（挡住启动）；运行期遇到任何 Redis 错误都该**放行**（只记日志）。**热路径一律 fail-open。**

**Q：限流要放在布隆/缓存之前还是之后？**

**之前。** 限流针对的是"这个 IP 太频繁"，**与短码合不合法无关**。若排在布隆之后：一个 IP 拿随机非法短码狂刷 → 布隆直接 404 → **不消耗配额** → 限流等于没装。

代价：跳转链路的 Redis 往返从 2 次变 **3 次**（限流 + 布隆 + 缓存）。

**Q：Lua 有哪些坑？（挑三个）**

| 坑 | 后果 |
|---|---|
| `ceil()` 写成全局（正确是 `math.ceil()`） | Lua **中途报错不回滚已执行的写** → `hset` 生效但 `expire` 没执行 → **TTL = -1、限流静默失效**，而 `HGETALL` 看起来桶正在正常扣减 → 降级把 bug 藏起来 |
| `ARGV` 传 `int`/`double` 而非字符串 | `ClassCastException`（**不是** `DataAccessException`，catch 接不住）→ 每个请求 500 |
| `now` 的单位没定死（毫秒当秒用） | `timePassed × rate` 被放大 1000 倍 → 桶永远满 → **零报错地失效** |

> 另外两条：Lua 变量必须 `local`（否则 `Script attempted to create global variable`）；**原子 ≠ 事务**，中途报错已执行的写**不回滚**。

## 十、访问统计：PV / UV 双算法（W6-A）

**Q：统计为什么不能写在跳转路径里？**

跳转要"**跳得过去**"，统计要"**看得见**"，两者节奏完全不同。统计要查库、要聚合，塞进最高频的路径就是给它加最重的负担。

所以拆成**两条独立路径**：写侧只记流水（W4 的 `RPUSH`），读侧由定时任务把流水算成聚合表。表也分两张：明细表**写多读少**、聚合表**读多写少**。

**Q：PV 和 UV 分别怎么算？⭐**

| 量 | 定义 | 算法 | 精度 |
|---|---|---|---|
| **PV** | 总访问次数 | 明细行数 `COUNT(*)` | 精确 |
| **UV** | 独立访客数 | HyperLogLog（`PFADD` / `PFCOUNT`） | 标准误差 **0.81%** |

**这段要能背出来**：PV 就是"数行数"，精确又便宜。UV 要"去重计数" —— 精确去重必须把所有访客都存下来（100 万人 = 100 万条记录），**内存随访客数线性增长**；HyperLogLog 用**固定 ≤12KB** 的概率结构给出 0.81% 误差的估算，**用一点点精度换掉"内存随规模线性涨"**。

**Q：为什么用"定时聚合"而不是实时 `GROUP BY` 或每次跳转 `INCR`？**

| 方式 | 代价 |
|---|---|
| 实时 `GROUP BY` 明细 | 几百万行会把库扫爆 |
| 每次跳转 `INCR` | 给最热路径加写负载，且**丢一次就永久错** |
| **定时聚合** ✅ | 数据延迟 ≤ 一个周期，换跳转路径零负担 |

**Q：聚合怎么写才幂等？**

覆盖式重算，靠 `(short_code, stat_date)` 唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE`，反复跑收敛到同一个值。

⚠️ `affectedRows` **有三种值**：INSERT 返 1、UPDATE 有变化返 2、**值没变返 0**。所以日志里的"行数"要记**入参**，**不能拿返回值当行数**。

**Q：`uv = VALUES(uv)` 有什么坑？**

HLL 的 key **有 TTL**、Redis 挂了也只能拿到 0 —— 这两种都会把**已经聚合好的 UV 覆盖成 0**。

判据：**只有"单调不减"的量才敢取大**（单天内 UV 不可能下降）→

```sql
uv = GREATEST(uv, VALUES(uv))
```

**Q：为什么强调"降级粒度 = 依赖粒度"？**

PV 只依赖 **MySQL**、UV 只依赖 **Redis**，两者可用性本来独立。第一版把 `PFCOUNT` 写在循环外 → 一挂全挂。改成 catch 包在**循环内部** → 失败只丢 UV、**PV 照常落地**。

一句话：**别让一个依赖的故障带走另一个依赖的数据。**

**Q：写侧和读侧对异常的处置一样吗？**

**方向相反**：

| | 写侧 `PFADD` | 读侧 `PFCOUNT` |
|---|---|---|
| 处置 | **让它冒泡**（不吞） | **吞掉**，只 `log.warn` |
| 理由 | 吞了会继续 `trim()` → 队列清空、**数据真丢** | 吞了只丢 UV（`GREATEST` 兜住不退），**PV 完好** |

判据不是"要不要 catch"，而是"**吞掉它，最坏的结果是什么**"。

**Q：`totalUv` 是什么语义？**

**"人日"，不是"人数"。** 聚合表每行是**某一天**的去重人数，跨天相加得到的是「人日」：同一个人 10-10、10-11 各来一次 → `SUM(uv)=2`，但"有多少人点过"= **1**。

根因：HLL 方案**只往聚合表存了数字、没存 HLL 本身**，查询时做不了跨天合并。

**面试话术**：我选"就 `SUM(uv)` 返 + 在字段注释写明人日语义"，因为**统计口径的"诚实"比"精确"更重要**；要做"区间去重人数"我知道怎么做（跨天 `PFMERGE`），但它把查询的可用性绑到了 Redis 上。

## 十一、压测：用计数器说话（W6-B）

**Q：压测主指标该看什么？**

**要选"不受环境干扰"的计数器。** 本机 Redis/MySQL 都走 Docker 端口转发，QPS 被环境高度污染；下面这些数字**因果链干净**：

| 想证明什么 | 看哪个计数器 |
|---|---|
| 布隆/缓存替 MySQL 挡住多少次查询 | MySQL `Com_select`（前后差） |
| 跳转路径有没有写库 | `Com_insert` 增量（**必须 = 0**） |
| 每请求几次 Redis 往返 | `INFO commandstats` 的 `calls` |
| 缓存命中率 | `INFO stats` 的 `keyspace_hits` / `keyspace_misses` |

⭐ **实测铁证**：布隆开/关的 **QPS 只差 9%**（1998 vs 1833），但 `Com_select` 是 **3 vs 27509**。**只看 QPS 会得出"布隆没啥用"的错误结论。**

**Q：冷/热对照怎么做才干净？**

**同一批数据打两遍** —— 第 1 遍必然全部未命中（回源 + 回填），第 2 遍必然全部命中。同一探针、同一并发、同一批码，两轮数字直接可比。

**不要**用"每请求 `DEL` 缓存"这种脏手法（`DEL` 自己也有往返，污染对照）。实测 `Com_select`：**3003 → 3**。

**Q：压测炸出了什么问题？**

1. **创建路径 P0**：`short_code` 是 Base62（**大小写敏感**），但列沿用了库默认的 `utf8mb4_0900_ai_ci`（**不敏感**）→ 唯一索引把 `10000A` 和 `10000a` 当成同一个值 → **创建失败率 17.9%**，而且换号重试治不好（病在列的排序规则上，不在号上）；
2. **队列无界增长**（W4 的设计缺陷，见 §八）；
3. **一次布隆判断要 8 次 Redis 往返**（1 次 `EXISTS` + 7 次 `GETBIT`），占跳转链路 10 次往返里的 **8 次** → 可用 `BITFIELD` 合并成 1 次。（**W6-B 已做**：`EXISTS` + `BITFIELD` = 2 次，见 `docs/05` §三之五十六）

> 判据：**当"编码方案"和"存储层的比较规则"表达的不是同一件事时，唯一索引会从"兜底"变成"误伤"。**

**Q：这个 P0 为什么藏了 6 周？**

**小规模测试覆盖不到"规模效应"。** 发号器从 `62⁵ = 9.16 亿` 起步，`seq 1..35` 生成的码末尾是数字/大写字母，**全都不撞**；到 `seq 36`（Base62 里第一个小写字母 `a`）才第一次撞上 `seq 10` 的 `'A'`。之前每次只造几条链接 → 一路绿灯。

> 判据：凡是"**随规模变化**"的性质（唯一索引冲突、队列长度、内存占用、连接池），**都必须造够数据再验** —— "能跑通"从来不等于"规模上没问题"。

**Q：怎么定位瓶颈？**

**先数清"一次请求花了多少次 Redis 往返"**（`INFO commandstats` 的 `calls` 前后差）：

| 命令 | 次数 | 用途 |
|---|---|---|
| `EVALSHA` | 1 | 限流令牌桶（Lua） |
| `EXISTS` | 1 | 布隆就绪标志 |
| `GETBIT` | 7 | 布隆的 7 个位 |
| `GET` | 1 | 跳转缓存 |
| **合计** | **10 次/请求** | ← 当时的结论 |

> ⚠️ 这张表**没算访问日志入队**。当时是 `RPUSH` + `LTRIM` 两条命令（W10 合成 1 次 EVAL）。
> 补上之后：W3 时点实际 **12 次**；W6-B 用 `BITFIELD` 把 7 次 `GETBIT` 收成 1 次后 **6 次**；W10 再把日志两条命令合并后 **5 次**（实测 `evalsha×2 + exists + bitfield + get` = 5）。
> 注意这张"`GETBIT` 7 次"的表**在 W6-B 之后就已经过期**了 —— 一个数字被写进文档后，改了其中一环就得回头重算它，否则它会以"历史记录"的身份冒充现状。
> 这个漏项本身也是个教训：**数往返要数"整条链路"，而不是"你正在优化的那一段"**。

> 优化前先数**全链路**的往返，否则会：低估基准（以为是 7 次、其实 10 次）、算错收益、**漏掉更省的那一刀**（那 1 次 `EXISTS` 查的是一个"只从 `false` 变 `true`"的标志，本来就不该走网络）。

**Q：压测数据能横向比吗？**

**不能跨批次比。** 同一份代码复跑，QPS 会掉 −8.5% ~ −41%（环境漂移可达 40%）→ **只合同一批次内比较**。

另外实测：`log-impl`（打印 SQL 日志）对 QPS **测不出影响** —— 说明"改了配置看不出效果"，可能是**这个因素根本不是瓶颈**。

## 十二、全链路 traceId（W7）

**Q：为什么要做全链路 traceId？**

一个请求在日志里会散成很多行（filter → interceptor → controller → service → MyBatis）。没有 traceId 时，并发日志互相穿插，**`GlobalExceptionHandler` 的报错根本没法关联到是哪个请求** —— 这就是 W7 的真实痛点。

**Q：怎么做？**

四步：① `TraceIdFilter`（最外层）造 id → 写 MDC + 响应头 `X-Trace-Id`；② 日志 pattern 读 MDC（`%X{traceId:-}`）；③ `TraceIdAdvice` 把 id 填进 `Result.traceId`；④ 跨层一致性验收。

**Q：为什么 filter 要放最外层？**

**想覆盖"所有出口"的东西，只能放链路最外层。**

```
请求 → [TraceIdFilter]                          ← 只有它覆盖"全部出口"
         ↓
      [RateLimitInterceptor]  ── 429 直接写 response（不过 controller）
         ↓
      [DispatcherServlet] → controller/service → 返回值
         ↓                                    ↑ ResponseBodyAdvice 在这里注 body
      @ExceptionHandler / @ControllerAdvice
         ↓
      响应（响应头 + body）
```

`response.setHeader()` 因为 filter 在最外层，**对所有出口都有效**；而 `Result.traceId` 只能覆盖"走 controller / 异常处理器"的出口 —— **302 和 429 是天然例外**（302 用 `.build()` 没有 body；429 压根不进 controller）。

**Q：`ResponseBodyAdvice.supports()` 为什么不能判断是不是 `Result`？⭐**

它的签名只给了**声明类型**，**拿不到 body**。而 `Result.class.isAssignableFrom(声明类型)` 会漏掉 `ResponseEntity<Result<...>>` 这类 —— 恰好是**跳转控制器的全部错误出口 + 404/405/415/500 框架错误码**，"**漏掉的正是最需要 traceId 的那部分**"。

所以口径是：**`supports` 恒返 `true`，判断下沉到 `beforeBodyWrite` 里用 `instanceof Result<?>` 过滤。**

```java
public boolean supports(...) { return true; }        // 判据下沉
public Object beforeBodyWrite(Object body, ...) {
    if (body instanceof Result<?> r) { r.setTraceId(MDC.get(MDC_KEY)); }
    return body;                                      // 原样返回，不要 new
}
```

> 判据：**当一个方法拿不到你判断所需的信息时，把判断下沉到拿得到信息的那一层。**

**Q：为什么注入必须"早于序列化"？**

`Result.traceId` 上有 `@JsonInclude(NON_NULL)`（值为 null 时不输出），而这个注解**是在 Jackson 序列化那一刻才求值的**。所以顺序必须是：

```
beforeBodyWrite（set traceId） → Jackson 序列化（求值 NON_NULL） → 输出 JSON
        ↑ 早                                                ↑ 晚
```

反过来（放进 `supports`、或在 filter 里事后改）→ 字段永远是 null、被 `NON_NULL` 吃掉、**不报任何错**。

**Q：MDC 有什么坑？**

**MDC = ThreadLocal**，挂在当前线程上，**不是"请求作用域"**。Tomcat 的工作线程从线程池一取一还 —— 不清 MDC，上一个请求的 id 会跟着线程回池子、**漏给下一个请求**。所以 filter 的 `finally` 里必须 `MDC.clear()`（用 `clear()` 而不是 `remove(key)`，为了兜住"下游有人放了东西忘清"）。

⭐ 一个反直觉的实测：**keep-alive 下"同连接 ≠ 同线程"** —— 同一条 TCP 连接（local port 同一个）连打 3 个请求，落在 **3 个不同的工作线程**上。Tomcat NIO 是"每请求从线程池取一个"，不是"一连接一线程"。**这恰恰说明 MDC 串号的风险是真实的。**

**Q：改日志格式要注意什么？**

`logging.pattern.console` 是**整体替换**、不是追加。Boot 默认那一行有 **7 个字段**（时间/级别/PID/`---`/应用名/线程/logger），只写 `"%X{traceId} %m%n"` → **前面 7 段全消失、且不报任何错**。所以新 pattern 要把这些字段**自己照搬一遍**。

两个细节：

- YAML 里 `%` 开头的值**必须加引号**，否则 SnakeYAML `ScannerException` → **启动失败**；
- **转换词写错不报错**，只把 `%PARSER_ERROR[xxx]` 烙进每一行（`%wEx` 是 Boot 注册的、不是 logback 内置）→ 干脆**不写异常转换词**，让 logback 自己补。

> 判据：改"格式类配置"前，先把**当前生效的格式原文抓出来** —— 这类配置多数是替换语义，"我加了一段"的直觉通常是错的。

**Q：怎么验证 traceId 真的生效？**

**看响应头 + 看日志的"天然对照组"。** 同一份日志、同一个 pattern、相隔 1.7 秒：

```
23:18:58.311 DEBUG [ITEM6-AAA] [nio-8080-exec-5] RedirectServiceImpl : 缓存未命中...
23:19:00.010  INFO []           [   scheduling-1] AccessLogFlushJob  : 搬运开始
```

一边有 id、一边空 `[]` → 排除"整个进程都打了同一个值"这种假通过。

⚠️ **看响应头，不要看日志行**：302 成功路径**不产生任何日志行**（访问日志只进 Redis 队列），`grep traceId` 得 0 **不是故障**。

## 十三、容器化部署（W8）

**Q：为什么要容器化？**

回答"**换一台机器怎么跑起来**"。看起来只是"加个 Dockerfile"，实际翻出三类东西：**配置里写死的值**、**构建时看不见的副作用**、**容器和本机不一样的默认值**。

**Q：开发和生产怎么共用一份 compose？**

给 `app` 服务打 `profiles: ["prod"]`：

```
docker compose up -d                         → mysql, redis（开发：本机 IDEA 跑应用）
docker compose --profile prod up -d --build  → mysql, redis, app（部署：全套）
```

**同一份文件、两种视图** —— 不用维护两份，也就不会有"两份配置悄悄漂移"。

**Q：`depends_on: service_healthy` 是必需品吗？⭐**

**不是"否则起不来"的必需品，而是"省掉启动瞬间那批脏响应"。** 因为 **Hikari 连接池是懒加载的**：

- Spring Boot 用"无参构造 + setter"建数据源 → 池在**首次 `getConnection()`** 才初始化；
- 所以**应用宣告"启动成功"的那一刻，一个数据库连接都还没建**。

实测 `MYSQL_HOST=wrong-host` 照样 **4.5s 启动成功**，只在 `/actuator/health`（**503**）和真请求（**500**）才暴露。

> 判据：**"启动成功"不等于"依赖可用"。**

**Q：`${X}` 和 `$$X` 有什么区别？⭐**

两条**完全不同的路**：

| 写法 | 谁替换 | 何时可用 |
|---|---|---|
| `${REDIS_PASSWORD}`（单 `$`） | **宿主机**（compose 解析文件时） | 任何地方都能用，值被"烙"进配置 |
| `$$REDIS_PASSWORD`（双 `$`） | **容器内的 shell** | **只有容器真的定义了这个 env 才可用** |

踩的坑：`command:` 里的 `${REDIS_PASSWORD}` 工作正常，但 healthcheck 里的 `$$REDIS_PASSWORD` 拿到**空串** → `AUTH failed` → redis 一直 `unhealthy` → `depends_on` 卡死 → **app 永远起不来**（因为 redis 的 `environment:` 里只有 `TZ`、没定义 `REDIS_PASSWORD`）。

> 判据：**看到 `$` 先问"这是谁在替换"**；如果是容器侧（`$$`），必须先确认容器里真的定义了这个变量 —— **"别处能用"不构成证据**。

**Q：`CMD` 和 `CMD-SHELL` 有什么区别？**

**`CMD` 数组（exec 形式）不过 shell → 变量永远展不开、通配符和管道也不生效。** 需要变量展开就走 `CMD-SHELL`（`$$` 先被 compose 还原成 `$`，再由 shell 展开）。

**Q：`.dockerignore` 到底管什么？**

**它是"构建上下文的准入名单"，不只是"瘦身"。** `COPY` 只能拿名单里的东西。

所以"排除 `target/`"和"从 `target/` 拷 jar"是**互斥**的 → 解法是 `!target/*.jar` 例外（**顺序敏感**，"最后匹配的规则生效"）：

```dockerignore
target/
!target/*.jar
```

**更重要的是它管着"有没有泄密"**：漏一个 `.env`，密码就会**焊进镜像层**，`docker history` 一捞就出来。

**Q：单阶段镜像有什么隐含前提？**

`COPY target/*.jar` 要求 **jar 必须先在** —— **compose 不会替你编译**。所以"一条命令起全套"实际是固定的两步：

```bash
mvn -DskipTests package
docker compose --profile prod up -d --build
```

**Q：为什么 `mvn package` 一定要 `-DskipTests`？⭐**

**"构建"也是"执行"，它会跑测试，而测试有副作用。**

```java
// RebuildBloomFilterTest
@AfterEach
void cleanUp() {
    stringRedisTemplate.delete(RedisKeyConstant.BLOOM_READY);
    stringRedisTemplate.delete(RedisKeyConstant.BLOOM);
}
```

而 **`@Transactional` 只能回滚 MySQL，回滚不了 Redis** → "跑一次打包"的后果是：数据库干干净净、**Redis 里的布隆位图被删了**。

> 判据：**凡是要跑测试/脚本的构建步骤，先问一句"它的副作用写在哪些外部系统上、能不能回滚"。回滚不了的，就别在构建里跑。**

**Q：容器里有哪些"默认值和本机不一样"？**

| 项 | 本机 | 容器默认 | 处理 |
|---|---|---|---|
| 时区 | `Asia/Shanghai` | **UTC** | `ENV TZ=Asia/Shanghai`（否则日志差 8 小时） |
| 数据 | 项目/系统目录 | **named volume**，`down` 不删 | 想从零重建必须显式 `down -v` |

> "容器是易耗品，数据不是" —— 实测 `down` 掉三个容器再 `up`，`t_short_link` 仍 3001 行。
